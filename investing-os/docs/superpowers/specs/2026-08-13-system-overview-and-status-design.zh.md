# Investing-OS / Stock Team 系统总览与状态文档设计

状态：已获用户方向确认，待书面规格复核
日期：2026-08-13

## 1. 目标

建立一份面向用户、后续高阶模型和开发协作者的权威系统地图，使读者不需要重新扫描仓库，就能回答：

- 这套系统为什么存在；
- `investing-os`、`stock_team`、Dashboard、用户分别负责什么；
- DAILY 与研究认知闭环如何运行；
- 哪些环节已经实现、哪些仅有文档或测试、哪些尚未重新验证；
- 2026 年 8 月恢复开发应从哪里开始。

正式产物路径固定为：

`investing-os/SYSTEM-OVERVIEW-AND-STATUS.zh.md`

## 2. 文档定位

这份文档是“导航与当前状态入口”，不是新的业务契约，也不替代已有权威文件：

- `PROJECT-CHARTER.zh.md`：项目目标、边界、统一术语与行动原则；
- `system/workflows/DAILY-CONTRACT.zh.md`：DAILY 详细业务契约；
- `system/workflows/WORKFLOW-STATUS.zh.md`：细粒度实现状态台账；
- 各 schema、测试和运行记录：具体行为证据。

总览文档只提炼这些来源，并为每项状态提供链接与最近核验日期。发生冲突时，不以总览文字覆盖专项契约，而是明确标注冲突并指向权威来源。

## 3. 目标读者

优先服务：

1. 用户本人：快速理解系统全貌和下一步；
2. 新接手的高阶模型：定向恢复，不重新扫描仓库；
3. 执行局部任务的低阶模型：理解边界，但仍必须依据具体任务包工作。

文档不面向自动交易，也不授予交易权限。

## 4. 内容结构

正式文档按以下顺序组织：

1. 一页摘要：当前系统定位、成熟度判断和最近核验日期；
2. 系统职责与边界；
3. 总体架构图；
4. DAILY 每日交易流程图；
5. Research / Evidence / Learning 认知闭环图；
6. `investing-os` 与 `stock_team` 握手图；
7. Dashboard 页面、数据来源和职责；
8. 工作流与核心能力实现状态矩阵；
9. Git、运行时与数据源现状；
10. 2026 年 8 月恢复路线；
11. 权威文件索引与状态维护规则。

## 5. 图表设计

所有结构图采用 Mermaid，避免维护独立图片并确保 Git 可审查。

### 5.1 总体架构图

展示四个主体：

```text
用户
↕ 讨论 / 确认 / 权限 / 最终判断
investing-os（认知与决策主脑）
↕ Evidence Request / Evidence Packet
stock_team（数据与计算肌肉）
↕ 市场、IBKR、行情供应商、官方与产业来源
外部事实世界
```

Dashboard 作为观察与导航界面连接到协调器、运行时产物和认知资料，但不拥有独立决策逻辑。

### 5.2 DAILY 流程图

完整展示：

```text
DAILY-0 晨间准备
→ DAILY-1 盘前决策
→ DAILY-2 开盘观察
→ DAILY-3 盘中管理
→ DAILY-4 盘后复盘
→ 归档 / 次日恢复
```

图中同时标明：

- 用户必须交互的位置；
- `stock_team` 生成事实产物的位置；
- `investing-os` 解释和形成计划的位置；
- 观察模式、无交易日、无操作与中断恢复等合法旁路。

### 5.3 认知闭环图

展示 V3 Alpha 主线：

```text
Question
→ Evidence
→ Hypothesis
→ Reality Validation
→ Consensus / Price / Behavior / Odds
→ Investment Decision
→ Review
→ Learning 候选
→ 用户批准后进入长期认知
```

明确新闻、社区观点和价格变化不能直接跳过 Evidence/Hypothesis 进入长期 Reality。

### 5.4 脑—肌握手图

分别展示研究和交易两条链：

- `investing-os` 定义问题与事实请求；
- `stock_team` 获取事实、计算并生成固定产物；
- `investing-os` 解释证据、检查认知冲突；
- 用户批准计划、例外、结论或经验吸收。

## 6. 状态表达规则

沿用项目现有状态词：

- `defined`
- `documented`
- `partial`
- `runnable`
- `verified`
- `blocked`
- `unknown`

总览文档不得根据文件存在、历史测试或旧聊天内容自行提升状态。每个状态必须包含：

- 最近核验日期；
- 证据链接；
- 当前已知缺口；
- 下一验收动作。

为了便于阅读，状态矩阵额外使用中文解释，但英文状态值保持不变。

## 7. 2026 年 8 月恢复基线

初始基线必须如实记录：

- 当前分支为 `codex/repository-cleanup-20260630`；
- 截至 2026-08-13，本地相对远端领先 55 个提交；
- 最近业务提交日期为 2026-07-22；
- 工作区存在用户未提交的认知方法论文档与运行时文件，本轮不擅自处理；
- DAILY 曾有较广测试覆盖和真实试跑，但 8 月尚未重新完成最小回归，因此当前不能标记为 `verified`；
- 研究数据库、Alpha Questions 和公司阅读报告已经形成原型，但 Evidence 自动生产链尚未闭环。

这些数字在正式文档生成时重新通过 Git 命令核验，不直接复制旧对话结论。

## 8. Dashboard 状态表达

文档区分三类界面：

- Operating Console：DAILY 主入口和状态导航；
- Growth Dashboard：认知、经验与研究成长展示；
- Evidence / Report 页面：事实包和公司研究阅读表面。

需要明确：

- Dashboard 读取状态与产物；
- 对话承担解释、选择和确认；
- Dashboard 不自行推导交易结论，也不替代协调器状态机；
- 当前页面可用性与后端数据真实性必须分别记录，不能因页面能打开就认定流程可运行。

## 9. 恢复路线

正式文档记录以下顺序，但不把未来工作写成已经完成：

1. 建立 8 月恢复基线；
2. 核验并同步未推送提交；
3. 在隔离 runtime 运行最小 DAILY 回归；
4. 验证交易日期、跨日恢复、盘前/实时价格和 Dashboard 展示；
5. 定位并以 TDD 修复首个真实阻塞；
6. DAILY 稳定后设计 Evidence 自动生产的下一最小切片。

## 10. 维护方式

总览文档是低频更新的系统地图；状态台账是高频更新的事实记录。

- 架构、边界或流程名称变化时，更新总览；
- 测试、运行结果或单个步骤状态变化时，优先更新 `WORKFLOW-STATUS.zh.md`；
- 如果状态变化影响整体成熟度，再同步更新总览摘要；
- 所有状态更新必须带日期、证据和 Git commit；
- 不把实时价格、账户数据或私有运行文件写入总览。

## 11. 验收标准

正式文档完成后应满足：

1. 新读者十分钟内能解释两个内核、两个闭环和用户确认点；
2. 图中不混用 DAILY 步骤、Evidence 产物阶段和实施 Phase；
3. 每个主要工作流都有当前状态、证据、缺口和下一动作；
4. 清楚区分“历史测试通过”“当前可试跑”和“已重新验证”；
5. 清楚说明 Dashboard 不是决策引擎；
6. 所有本地文件链接使用仓库相对路径，避免生成错误的 `file:///C:/abs/path/...` 地址；
7. 不包含账户事实、私有成交、密钥或运行时敏感数据；
8. 与 `PROJECT-CHARTER.zh.md` 和 `WORKFLOW-STATUS.zh.md` 不发生边界冲突。
